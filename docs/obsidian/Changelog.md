### Changed
- **2026-07-22**: Tenant Profile's "Actions" sheet (`PrimaryActionsBar.tsx`) had two entries — "Create Charge" and "Create Rent" — that opened the exact same `CreateObligationModal` with the exact same effective result: the modal's obligation-type selector already defaults to `RENT`, so "Create Rent" was passing `initialValues={{obligationType:'RENT'}}` to override a default that was already `'RENT'`. Removed "Create Rent" entirely (owners can still pick Rent, or any of the 10 other obligation types, from "Create Charge"'s own type dropdown) and grouped the remaining 7 actions into four labeled sections on the mobile sheet (Collect / Charges & Receipts / Agreement / Tenancy) instead of one flat list, with a matching separator added between agreement actions and Check-out/Exit in the desktop "More" dropdown. `onCreateRent` prop removed from `PrimaryActionsBarProps`.
- **2026-07-22**: Tenant Profile's obligation actions (`ObligationCard.tsx`) simplified after feedback that Cancel/Waive/"Delete" were hard to tell apart. There is no Delete action in the code — the perceived third option was almost certainly **Edit**, whose own copy admits it "creates a corrected replacement and cancels the original" (see `Business-Rules.md` — Obligation Lifecycle). The real, non-mergeable confusion was that **Cancel** and **Waive** could render simultaneously as two identical-looking red buttons on a `PENDING` obligation. Fixed by deriving `hasPayments` from `obligation.payments[]` and showing exactly one: Cancel Charge (zero payments) or Waive Balance (any payment made) — same precondition the backend already enforces, just surfaced once instead of as a guess. Also renamed the Waive modal's dismiss button from "Cancel" to "Back" to stop reusing "Cancel" for two different meanings. See [[Business-Rules]].
- **2026-07-22**: Owner Home (`PortfolioView.tsx`) decluttered and given a universal search bar, per direct feedback referencing an alternate design. Removed three sections found redundant once the single-state Priority Card already surfaces the top-priority action: "Today's actions" (a bulleted list of the same overdue/move-out/activation/vacancy signals already in the KPI grid and Priority Card), "Needs attention" (a per-tenant overdue detail list duplicating what `/alerts` already owns), and "Business Health Trend" (the `PortfolioRevenueChart` component, a 6-month revenue/expense/profit chart with Top Profit/Low Occupancy/Top Dues chips) — the last of these had no other consumer, so `PortfolioRevenueChart.tsx` (339 lines) was deleted outright rather than left as dead code. Added a small "Snapshot" eyebrow label above the Beds/Outstanding/Revenue tiles for scannability. The page's own hostel-name/city search box (for filtering the Properties list further down) is unchanged and unrelated to the new universal bar below.
- **2026-07-22**: The new universal search bar was rebuilt after first-pass feedback that it redirected to the Tenants page instead of actually searching — new `UniversalSearchBar.tsx` (`app/components/portfolio/`) reuses the existing owner-scoped, all-hostels `paymentService.quickCollectSearch()` (already used by `RecordPaymentModal.tsx` for the same name/phone/room_no matching, no new backend endpoint) and renders matches as an inline dropdown under the input — debounced 250ms, click-outside/Escape to close, no navigation until a specific result is clicked (→ `/hostels/:hostel_id/tenants/:id`). ### Added
- **2026-07-22**: New `formatIST()` helper (`backend-next/lib/timezone.ts`) — a real bug fix, not a style tweak. Every backend "en-IN" date/time format call (`expense-export-service.ts`'s "Generated at"/footer date in CSV, XLSX, and PDF exports) was calling `.toLocaleString("en-IN")`/`.toLocaleDateString("en-IN")` with no explicit `timeZone`, which resolves to the *server process's own* timezone in Node (commonly UTC on cloud hosts) — silently mislabeling a UTC time with Indian formatting instead of actually converting it, so an export generated at, say, 1:00 AM IST could show "Generated at: 7:30 PM" the previous day. Also fixed a same-class bug in `reportDateLabel()`'s month-range check, which used server-local `.getFullYear()/.getMonth()` on a `@db.Date` (UTC-midnight-encoded) value — switched to UTC getters. Frontend: `ActivityLogsView.tsx`'s three date/time formatters (day grouping, per-item time, detail panel) gained explicit `timeZone: 'Asia/Kolkata'` for the same reason (a non-IST browser was rendering Indian-locale-*formatted* but not actually IST-*converted* times); "Today"/"Yesterday" grouping now compares IST calendar-day keys instead of the browser's local `toDateString()`. Expenses: `ExpenseDetailsModal.tsx` gained a new "Added on" row showing `created_at` (when the expense was entered) alongside the existing "Date" row (the expense's own transaction date) — previously `created_at` wasn't surfaced anywhere in the expense UI. Both `ExpenseCard.tsx` and `ExpenseDetailsModal.tsx`'s existing date formatting also gained explicit `timeZone`. See [[Bugs]] (Expense/activity-log timestamps could silently show the wrong time on a non-IST server or browser).
- **2026-07-22**: Activity Logs — expense update/delete events were being silently dropped. `app/api/owner/activity-logs/route.ts`'s `activity_logs` query filtered `entity_type: { in: ['HOSTEL_POLICY', 'RENT'] }`, which excluded `EXPENSE` rows entirely (written correctly by `activityService.log()` on every expense update/delete, per `lib/events/index.ts`) and also excluded `AGREEMENT_TEMPLATE` rows despite the mapper below already having a branch to handle them — the same "written but never read" bug for two different entity types. Fixed by broadening the query to an `OR` covering both, scoping `EXPENSE` to `action_type: {in: ['UPDATE','DELETE']}` only (CREATE is already reconstructed from the live `expenses` table with cash-position enrichment the log's metadata doesn't have — duplicating it would double-count). Now editing or deleting an expense shows up in the Activity Log; previously an update silently changed the displayed entry in place with no edit trail, and a delete made the entire event vanish with zero record. See [[Bugs]].
- **2026-07-22**: Hostel lifecycle confirmation modals now show the real blast radius before the owner confirms. New shared `HostelImpactSummary.tsx`, rendered in both `PauseHostelModal.tsx` and `CloseHostelModal.tsx`, sourced from stats already on the hostel's own portfolio card (`active_tenants`/`occupied_beds`/`pending_dues` — no new fetch). `CloseHostelModal` additionally disables its submit button and swaps in a "Move tenants out first" state whenever the hostel has active tenants, instead of letting the owner submit and only then hit the backend's `prevent_archive_with_active_allocations` trigger error — it now also points them at "Temporarily Close" as the non-blocking alternative. Wired from both card surfaces that render `HostelActionMenu` (`PortfolioView.tsx`, `HostelsView.tsx`). See [[Bugs]] (Pausing a hostel gave no warning it stops rent generation for active tenants).

- **2026-07-20**: Business Recovery Platform — first three payment-correction handlers, all registered into `correctionRegistry` and driven through the `correction_cases` lifecycle (`createCase → preview → validate → execute`): **Reverse Payment** (`PAYMENT_REVERSAL`, reverses one payment's effect on its obligation via a new offsetting `payments` row + `LEDGER_CORRECTION` ledger debit, never mutating the original payment), **Transfer Payment** (`PAYMENT_TRANSFER`, reverses the source payment and re-allocates the same amount to a target tenant's open obligations via the existing FIFO settlement engine), and **Edit Reference/Notes** (`PAYMENT_REFERENCE_EDIT`, the one handler that performs a direct update — but only to `payment_groups.reference_number`/`notes`, never to `payments`). See [[Business-Rules]] (Correction Cases — Payment corrections), [[Database]].
- **2026-07-20**: Business Recovery Platform — `/api/recovery/cases/*` HTTP routes (`GET /api/recovery/cases` list, `POST /api/recovery/cases` create+auto-preview, `GET /api/recovery/cases/[id]` detail incl. event trail, `POST /api/recovery/cases/[id]/validate`, `POST /api/recovery/cases/[id]/execute` — also the retry entrypoint for `FAILED` cases), exposing the Reverse/Transfer/Edit-Reference correction handlers over HTTP for the first time. ### Added — Expense Export
- `GET /api/expenses/export` (`backend-next/app/api/expenses/export/route.ts`) — streams CSV/XLSX or generates a PDF report of expenses matching the same filters as `GET /api/expenses`. Built on a new shared query builder, `buildExpenseLedgerWhere()` (extracted from `expense-service.ts::getAllExpenses`, which now calls it too), so exported rows can never drift from what the UI's list/filters show. Rate-limited to 10 exports/min/owner.
- `lib/services/expense-export-service.ts` — format/scope-agnostic export core, deliberately decoupled from HTTP (no `NextRequest`/`Response`) so a future scheduled-export cron or saved-report-template runner can call the same generators without redesigning anything:
  - CSV and XLSX are true streams — batched `findMany` (500 rows/batch) feeds a `ReadableStream` (hand-rolled CSV) or an `exceljs` `WorkbookWriter` (genuine incremental zip writer, piped via a Node `PassThrough` → `Readable.toWeb()`) — memory stays bounded regardless of total export size.
