### Owner Action Registry
- **Status:** shipped (catalog-only slice)
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `backend-next/src/services/owner-actions/owner-action-registry.ts` (in-memory registry, `listForEntity(entity, ctx)`), `backend-next/src/services/owner-actions/definitions/*.ts` (`tenant-actions.ts` → `TENANT_EDIT_PERSONAL_INFO`; `payment-actions.ts` → `PAYMENT_RECEIVE`; `room-actions.ts` → `ROOM_MOVE`), `backend-next/src/services/owner-actions/bootstrap.ts` (single import point for all definitions), `backend-next/app/api/owner-actions/route.ts`, `frontend-v2/src/features/owner-actions/api/index.ts`
- **Depends on:** [[APIs]] (`GET /api/owner-actions`)
- **Notes:** A read-only catalog of which owner-facing actions are available for a given entity (currently only `tenant` is queried by the frontend). Each registered action declares `entity`, `category` (`EDIT`/`WORKFLOW`/`CORRECTION`/`VIEW`), a `label`, `allowedRoles`, and a synchronous `isAvailable(ctx)` predicate (evaluated server-side against `tenantStatus`/`actorRole`). `TenantProfilePage.tsx` fetches the tenant's action list and uses it to source the labels on the "Request Change" (`TENANT_EDIT_PERSONAL_INFO`, available only when tenant status is `ACTIVE`) and "Receive Payment" (`PAYMENT_RECEIVE`, always available) buttons on `PrimaryActionsBar`, falling back to hardcoded defaults if the catalog lookup misses. **This is catalog-only in this first slice — no action's actual execution routes through the registry yet** (clicking the buttons still triggers the pre-existing change-request/payment flows directly); the registry exists so future `CORRECTION`-category actions (payment reversal/transfer, expense void, etc. — see the Business Recovery Platform / correction-cases proposal work under `docs/business-logic/`, not yet reflected elsewhere in this vault) have a place to register into without inventing a new mechanism. `ROOM_MOVE` (`entity: "room"`) is registered but has no frontend consumer yet — deliberately out of scope for this slice.

### Resend Expired Renewal Offer
- **Status:** shipped 2026-08-22
- **Owner-facing?** yes · **Tenant-facing?** no (the tenant just receives the offer notification again)
- **Key files:** `backend-next/src/services/tenants/renewal-offer-service.ts` (`resendOffer`), `backend-next/app/api/agreements/renewal-offers/[id]/resend/route.ts`, `frontend-v2/src/features/agreements/api/index.js` (`agreementService.resendRenewalOffer`), `frontend-v2/src/app/components/views/RenewalQueueView.tsx` (`resendOfferMutation`, new `Expired` filter chip), `frontend-v2/src/app/components/views/renewal/RenewalOffersList.tsx` (Resend Offer button + expiry line), `frontend-v2/src/app/components/views/RenewalWorkspaceView.tsx` (Resend in the Offer History tab)
- **Depends on:** [[APIs]] (`POST /api/agreements/renewal-offers/[id]/resend`), [[Business-Rules]] (Agreement renewal — resending a lapsed offer), [[Database]] (`RenewalOffer`, `RenewalTimelineEvent`)
- **Notes:** Before this, an offer the tenant never responded to was a dead end in the owner UI — `expireStaleOffers` flipped it to `EXPIRED` and no action rendered on the row at all, so the owner's only route back was generating a whole new offer. Resend puts the *same* offer back in front of the tenant on the *same* terms with a fresh 15-day window, and re-fires the `renewal_offer_sent` event so the WhatsApp/email notification goes out again. It deliberately reuses the same `renewal_offers` row rather than cloning it the way `reviseOffer` does — a resend changes no terms, so a second row would duplicate the offer history without recording anything new; the "it lapsed and was sent again" fact is captured on the timeline instead (`OFFER_EXPIRED`, then `OFFER_SENT` carrying `metadata.resend`). Deposit figures are recomputed on resend, since the tenant's deposit position can have moved since the first send. The button also appears on an offer that is past its window but still marked `DRAFT`/`SENT`, because `expireStaleOffers` only runs on the daily lifecycle job and `acceptOffer` already rejects such an offer as expired — it is dead to the tenant either way. Revise is now offered on expired (and declined) offers too, for the "re-offer, but on new terms" case — see [[Bugs]] for the guard bug that made the existing Revise button dead on declined offers.

### Correct Payment (Reverse / Transfer)
- **Status:** shipped (Reverse + Transfer — first real UI consumer of the Business Recovery Platform's `/api/recovery/cases/*` routes)
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `frontend-v2/src/features/recovery/api/index.ts` (`recoveryService.createCase/validate/execute/getById`), `frontend-v2/src/app/components/modals/CorrectPaymentModal.tsx` (self-contained correction-type toggle → reason (+ tenant picker for Transfer) → preview → confirm modal), `frontend-v2/src/features/payments/api/index.js` (`paymentService.quickCollectSearch`, reused for the Transfer "correct tenant" search, same pattern as `RecordPaymentModal.tsx`), `frontend-v2/src/features/tenants/components/financial/FinancialActivityCard.tsx` (`onCorrectPayment` prop, "Correct Payment" button next to "View Receipt"), `UnifiedActivityTimeline.tsx` (threads the prop), `frontend-v2/src/features/tenants/components/profile/TenantProfilePage.tsx` (`correctingPaymentId` state, renders the modal, invalidates `queryKeys.tenants.{obligations,financialTimeline,advance,full,overview}` on close)
- **Depends on:** [[APIs]] (Recovery / Corrections), [[Business-Rules]] (Correction Cases — Payment corrections)
- **Notes:** Wired directly into the Tenant Details page's Activity tab's unified timeline per an explicit product decision to **not** build a separate Recovery Center dashboard in this phase (that list/detail view is deferred to Phase 3). This bypasses the Owner Action Registry entirely — it does not register as a `CORRECTION`-category owner action; the "Correct Payment" button is a conditional render (`receiptPaymentId && onCorrectPayment && canCorrectPayment`) alongside the existing "View Receipt" button, not sourced from `ownerActionsService`. The third condition (`canCorrectPayment = payments.length <= 1`) hides the button for grouped/multi-payment settlement entries — see [[Bugs]] — because reversing/transferring one payment in a group would only be a partial correction of the card's total. The modal now opens with a two-button correction-type toggle ("Wrong / Reverse" vs "Wrong Tenant / Transfer", pre-preview only — hidden once a case exists). Reverse mode is unchanged: `createCase({caseType: 'PAYMENT_REVERSAL', input: {paymentId}})`. Transfer mode additionally requires picking a destination tenant via a debounced (250ms) `paymentService.quickCollectSearch` lookup (fires only when the query is ≥2 chars and no tenant is yet selected) before "Preview Impact" is enabled, then calls `createCase({caseType: 'PAYMENT_TRANSFER', input: {paymentId, toTenantId}})`. Both modes share the same preview → "Confirm Reversal"/"Confirm Transfer" → `validate` + `execute` flow (treated as one logical confirm step; a 422 `VALIDATION_REJECTED` from `validate` stops `execute` from running and shows the rejection reason inline). Edit Reference/Notes (`PAYMENT_REFERENCE_EDIT`) UI is still explicitly out of scope for this slice — the backend handler exists and is reviewed, but has no frontend entry point yet. Reverse mode also supports a guided immediate re-record for the "wrong amount" case: `CorrectPaymentModal` accepts an optional `onSuccessReverse?: (tenantId: string) => void` callback, invoked only when `correctionType === 'REVERSE'` (never Transfer, since a Transfer's money has already moved to the correct tenant, leaving nothing to re-record). `TenantProfilePage.tsx` wires this to reopen the existing Receive Payment flow (`RecordPaymentModal`, reusing the page's existing payment-modal state — no second mount point was introduced) about 1.3s after the reversal's own success state finishes displaying, scoped to the same tenant whose payment was just reversed.

### Change Rent
- **Status:** shipped
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `frontend-v2/src/features/tenants/api/index.js` (`tenantService.changeRent`), `frontend-v2/src/app/components/modals/ChangeRentModal.tsx` (self-contained FORM → CONFIRM flow, mirroring `WaiveObligationModal.tsx`'s identity-confirmation pattern), `frontend-v2/src/features/tenants/components/profile/TenantProfilePage.tsx` (`showChangeRent` state, "Change Rent" surfaced as one of `PrimaryActionsBar`'s own overflow ("More") menu actions — not a separate adjacent button — gated on `canChangeRent` (tenant status `ACTIVE`), `upcomingRentObligations` derived from the page's already-loaded `dues.items` — no second obligations fetch)
- **Depends on:** [[APIs]] (`POST /api/tenants/:id/change-rent`), [[Business-Rules]] (rent changes are immediate and owner-only, see the Category C exception note)
- **Notes:** Owner picks a new rent amount, the month it should take effect from (dropdown sourced from `upcomingRentObligations` — RENT obligations from the page's existing dues data with zero recorded *net* payments, `Number(o.paid ?? 0) === 0`), and a reason → password re-entry (`identityService.confirmIdentity(password, 'CHANGE_RENT')`) → submit. Applies immediately with no tenant approval step (identity-token gated the same as obligation cancel/waive). On success, invalidates `queryKeys.tenants.{obligations,financialTimeline,advance,full,overview}` and calls the page's `refetch()`. `currentRent` is read from `tenant?.monthly_rent ?? overview?.rent`. `applyRentChangeInTx` now also writes `tenants.monthly_rent` (in the same transaction as `agreement.contract_rent`, mirroring the `tenantContractSync` pattern used by renewal activation in `renewal-activation-engine.ts`) — resolves the previously-flagged "Unknown / needs clarification": `tenant.monthly_rent` **is** kept in sync, so this displayed value no longer goes stale after a successful change. See [[Bugs]] for this fix and a second, related gap: the modal's pre-submit "N installments will change" preview is a client-side count filtered by *net* zero-paid, which is a looser guard than the backend's real safety rule (zero payment *records* on the obligation, `payments.length === 0`) — after a Payment Reversal correction (see Correct Payment above), an obligation can have net paid `0` via two payment rows (original + offsetting reversal) and still be correctly skipped by the backend while still appearing in the frontend's preview count. The modal does not attempt to prevent this (would require exposing raw payment-row counts through `getTenantDues()`, out of scope); instead its success screen now shows the server-reported `obligationsUpdated` count from the response, so any such discrepancy is visible after the fact instead of silent.

### Tenant Profile UI/UX consolidation
- **Status:** shipped
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `frontend-v2/src/features/tenants/components/profile/TenantProfilePage.tsx` (orchestrator — now ~840 lines, down from having 6 overlapping sections), `RiskComplianceCard.tsx` (replaces `TenantHealthCard.tsx` + `OwnerInsights.tsx`), `UnifiedActivityTimeline.tsx` (replaces `FinancialActivity.tsx` + `LedgerStatement.tsx` + `ActivityTimeline.tsx`, and absorbs invitation-history logs that previously had their own standalone card), `DocumentsTab.tsx` (replaces the separate KYC verification card + the old `DocumentsHub` section), `frontend-v2/src/features/tenants/components/financial/PrimaryActionsBar.tsx` (extended — primary "Receive Payment" button + 3 secondary buttons — Create Charge, Create Rent, View Receipts — + a "More" overflow menu — Share Payment Link, Request Change/Edit Details, Change Rent (conditional on `canChangeRent`), Check-out/Exit), `frontend-v2/src/app/components/ui/tabs.tsx` (real `Tabs`/`TabsList`/`TabsTrigger`/`TabsContent` primitive, replacing the deleted `FinancialWorkspaceNav.tsx` fake scroll-nav)
- **Depends on:** [[Frontend]] (page structure), existing services only — `financial-read-model-service.ts`, `tenantService`, `paymentService`, `ownerService`, `useTenantProfile`, `useOwnerActions`, `useTenantChangeRequests` are all reused unchanged
- **Notes:** Four-part consolidation of a page that had accumulated redundant sections over several prior feature slices (Owner Financial Workspace, Change Rent, Correct Payment). (1) `RiskComplianceCard` merges what used to be two independently-derived agreement/KYC/score cards (`TenantHealthCard`'s composite score + checklist, `OwnerInsights`'s prose warnings restating the same checklist items) into one checklist-first card. (2) The page's detail region is now real `Tabs` (`TabId = 'obligations' | 'activity' | 'documents' | 'stay'`, `activeTab` state) instead of the deleted `FinancialWorkspaceNav`'s scroll-into-view fake navigation. (3) `UnifiedActivityTimeline` (the Activity tab) merges what used to be three-to-four separate feeds — "Financial Activity" (payments/obligations events), "Ledger & Accounting Statement" (`advance` ledger entries), a standalone "Recent Activity" card, and a standalone "Invitation History Logs" card — into one filterable timeline, still surfacing the "Correct Payment" button per payment entry (see Correct Payment (Reverse / Transfer) above) via the same `onCorrectPayment` prop threaded through `FinancialActivityCard.tsx`. (4) `DocumentsTab` merges a standalone KYC verification card with the pre-existing `DocumentsHub` into one tab. Separately, the page's action layout (previously 3 groups totaling 8 buttons, including a standalone "Change Rent" button rendered next to the action bar) is now one `PrimaryActionsBar`: 1 primary + 3 secondary always-visible buttons, plus a "More" dropdown/bottom-sheet holding the remaining 4 actions (Share Payment Link, Request Change, Change Rent, Check-out/Exit) — `canChangeRent`/`onChangeRent` props gate the Change Rent item to `ACTIVE` tenants only, same rule as before. A 4th "Stay" tab (room allocation history via `AllocationHistoryTimeline` + the move-out settlement workflow via `ExitWorkflowSection`) was added, replacing what was previously a collapsible card lower on the page. **Purely a frontend recomposition — no backend routes, services, or business rules changed.** See [[Frontend]] for the resulting always-visible-zone + 4-tab structure, and [[Changelog]] for the dated entry.

### Flexible Payment Links (amount-flexible, tenant-scoped + tenant self-service generation)
- **Status:** shipped
- **Owner-facing?** yes (pre-existing, `PrimaryActionsBar`'s "Share Payment Link" — see Tenant Profile UI/UX consolidation above) · **Tenant-facing?** yes (link generation from `/tenant/financials`, plus the payer-facing `/pay/[token]` page itself, which needs no login)
- **Key files:** `backend-next/src/services/payments/payment-link-service.ts` (`PaymentLinkService.getOrCreateToken` — `obligation_id` is now an optional default-amount hint, no longer resolved-and-required; unconditionally mints a tenant-scoped token even with zero outstanding obligations), `backend-next/app/api/payments/pay-link/route.ts` (accepts `TENANT`-role sessions in addition to `OWNER`; a tenant session is force-scoped to its own `session.tenant_id` and forbidden from passing `obligationId` — only an owner may target an arbitrary tenant/obligation), `backend-next/app/api/payments/pay/[token]/route.ts` (payer page now renders an editable amount input instead of a fixed obligation balance, with a live `preview` action showing the FIFO settlement breakdown as the payer types, and a default/checkout branch that calls the new `paymentService.createAmountPaymentIntent`), `backend-next/src/services/payments/payment-service.ts` (`createAmountPaymentIntent` — amount-first counterpart to `createMultiObligationPaymentIntent`, builds its obligation set from `PAYABLE_STATUSES` and feeds it through `buildSettlementPlan`), `frontend-v2/src/portal/pages/TenantFinancialsPage.tsx` (`handleSharePaymentLink` handler + a "Share Payment Link" button rendered next to "Make Payment" in the Financial Health hero card), `frontend-v2/src/features/payments/api/index.js` (`paymentService.generatePayLink({ tenantId, obligationId })`, pre-existing wrapper, reused unchanged).
- **Depends on:** [[APIs]] (`POST /api/payments/pay-link`, `/api/payments/pay/[token]`), [[Business-Rules#Flexible payment links]], [[Database]] (`payment_link_tokens`), [[Decisions]] ADR-017, `src/services/payments/settlement-planner.ts::buildSettlementPlan` (the same FIFO engine offline "Receive Payment" uses).
- **Notes:** Multi-task branch. Earlier tasks made `payment_link_tokens.obligation_id` nullable and `getOrCreateToken` obligation-optional (so "Share Payment Link" now shows regardless of outstanding dues), then opened `POST /api/payments/pay-link` to `TENANT` sessions (self-generation, scoped strictly to their own account, tested in `backend-next/tests/pay-link-tenant-auth.test.ts`), then reworked the payer-facing `/pay/[token]` page to accept any entered amount with a live FIFO-allocation preview rather than a fixed pre-picked obligation balance. The final task added the tenant-portal UI entry point so a tenant can copy a `/pay/<token>` link (from the response's `url` field) to send to a guardian or anyone paying on their behalf, without needing the owner to generate it for them. `TenantFinancialsPage.tsx` is technically under the frozen `src/portal/` tree (see [[Frontend]]) — this was an in-place edit to an already-allowlisted file, not a new file, so `check-architecture.mjs`'s allowlist was not touched.
