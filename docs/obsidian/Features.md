### Owner Action Registry
- **Status:** shipped (catalog-only slice)
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `backend-next/src/services/owner-actions/owner-action-registry.ts` (in-memory registry, `listForEntity(entity, ctx)`), `backend-next/src/services/owner-actions/definitions/*.ts` (`tenant-actions.ts` → `TENANT_EDIT_PERSONAL_INFO`; `payment-actions.ts` → `PAYMENT_RECEIVE`; `room-actions.ts` → `ROOM_MOVE`), `backend-next/src/services/owner-actions/bootstrap.ts` (single import point for all definitions), `backend-next/app/api/owner-actions/route.ts`, `frontend-v2/src/features/owner-actions/api/index.ts`
- **Depends on:** [[APIs]] (`GET /api/owner-actions`)
- **Notes:** A read-only catalog of which owner-facing actions are available for a given entity (currently only `tenant` is queried by the frontend). Each registered action declares `entity`, `category` (`EDIT`/`WORKFLOW`/`CORRECTION`/`VIEW`), a `label`, `allowedRoles`, and a synchronous `isAvailable(ctx)` predicate (evaluated server-side against `tenantStatus`/`actorRole`). `TenantProfilePage.tsx` fetches the tenant's action list and uses it to source the labels on the "Request Change" (`TENANT_EDIT_PERSONAL_INFO`, available only when tenant status is `ACTIVE`) and "Receive Payment" (`PAYMENT_RECEIVE`, always available) buttons on `PrimaryActionsBar`, falling back to hardcoded defaults if the catalog lookup misses. **This is catalog-only in this first slice — no action's actual execution routes through the registry yet** (clicking the buttons still triggers the pre-existing change-request/payment flows directly); the registry exists so future `CORRECTION`-category actions (payment reversal/transfer, expense void, etc. — see the Business Recovery Platform / correction-cases proposal work under `docs/business-logic/`, not yet reflected elsewhere in this vault) have a place to register into without inventing a new mechanism. `ROOM_MOVE` (`entity: "room"`) is registered but has no frontend consumer yet — deliberately out of scope for this slice.

### Correct Payment (Reverse / Transfer)
- **Status:** shipped (Reverse + Transfer — first real UI consumer of the Business Recovery Platform's `/api/recovery/cases/*` routes)
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `frontend-v2/src/features/recovery/api/index.ts` (`recoveryService.createCase/validate/execute/getById`), `frontend-v2/src/app/components/modals/CorrectPaymentModal.tsx` (self-contained correction-type toggle → reason (+ tenant picker for Transfer) → preview → confirm modal), `frontend-v2/src/features/payments/api/index.js` (`paymentService.quickCollectSearch`, reused for the Transfer "correct tenant" search, same pattern as `RecordPaymentModal.tsx`), `frontend-v2/src/features/tenants/components/financial/FinancialActivityCard.tsx` (`onCorrectPayment` prop, "Correct Payment" button next to "View Receipt"), `FinancialActivity.tsx` (threads the prop), `frontend-v2/src/features/tenants/components/profile/TenantProfilePage.tsx` (`correctingPaymentId` state, renders the modal, invalidates `queryKeys.tenants.{obligations,financialTimeline,advance,full,overview}` on close)
- **Depends on:** [[APIs]] (Recovery / Corrections), [[Business-Rules]] (Correction Cases — Payment corrections)
- **Notes:** Wired directly into the Tenant Details page's Financial Activity feed per an explicit product decision to **not** build a separate Recovery Center dashboard in this phase (that list/detail view is deferred to Phase 3). This bypasses the Owner Action Registry entirely — it does not register as a `CORRECTION`-category owner action; the "Correct Payment" button is a conditional render (`receiptPaymentId && onCorrectPayment && canCorrectPayment`) alongside the existing "View Receipt" button, not sourced from `ownerActionsService`. The third condition (`canCorrectPayment = payments.length <= 1`) hides the button for grouped/multi-payment settlement entries — see [[Bugs]] — because reversing/transferring one payment in a group would only be a partial correction of the card's total. The modal now opens with a two-button correction-type toggle ("Wrong / Reverse" vs "Wrong Tenant / Transfer", pre-preview only — hidden once a case exists). Reverse mode is unchanged: `createCase({caseType: 'PAYMENT_REVERSAL', input: {paymentId}})`. Transfer mode additionally requires picking a destination tenant via a debounced (250ms) `paymentService.quickCollectSearch` lookup (fires only when the query is ≥2 chars and no tenant is yet selected) before "Preview Impact" is enabled, then calls `createCase({caseType: 'PAYMENT_TRANSFER', input: {paymentId, toTenantId}})`. Both modes share the same preview → "Confirm Reversal"/"Confirm Transfer" → `validate` + `execute` flow (treated as one logical confirm step; a 422 `VALIDATION_REJECTED` from `validate` stops `execute` from running and shows the rejection reason inline). Edit Reference/Notes (`PAYMENT_REFERENCE_EDIT`) UI is still explicitly out of scope for this slice — the backend handler exists and is reviewed, but has no frontend entry point yet. Reverse mode also supports a guided immediate re-record for the "wrong amount" case: `CorrectPaymentModal` accepts an optional `onSuccessReverse?: (tenantId: string) => void` callback, invoked only when `correctionType === 'REVERSE'` (never Transfer, since a Transfer's money has already moved to the correct tenant, leaving nothing to re-record). `TenantProfilePage.tsx` wires this to reopen the existing Receive Payment flow (`RecordPaymentModal`, reusing the page's existing payment-modal state — no second mount point was introduced) about 1.3s after the reversal's own success state finishes displaying, scoped to the same tenant whose payment was just reversed.

### Change Rent
- **Status:** shipped
- **Owner-facing?** yes · **Tenant-facing?** no
- **Key files:** `frontend-v2/src/features/tenants/api/index.js` (`tenantService.changeRent`), `frontend-v2/src/app/components/modals/ChangeRentModal.tsx` (self-contained FORM → CONFIRM flow, mirroring `WaiveObligationModal.tsx`'s identity-confirmation pattern), `frontend-v2/src/features/tenants/components/profile/TenantProfilePage.tsx` (`showChangeRent` state, "Change Rent" button rendered next to `PrimaryActionsBar` when tenant status is `ACTIVE`, `upcomingRentObligations` derived from the page's already-loaded `dues.items` — no second obligations fetch)
- **Depends on:** [[APIs]] (`POST /api/tenants/:id/change-rent`), [[Business-Rules]] (rent changes are immediate and owner-only, see the Category C exception note)
- **Notes:** Owner picks a new rent amount, the month it should take effect from (dropdown sourced from `upcomingRentObligations` — RENT obligations from the page's existing dues data with zero recorded payments, `Number(o.paid ?? 0) === 0`, mirroring the backend's own zero-payments repricing guard in `applyRentChangeInTx` so the affected-installment count shown in the modal can never diverge from what the backend actually reprices), and a reason → password re-entry (`identityService.confirmIdentity(password, 'CHANGE_RENT')`) → submit. Applies immediately with no tenant approval step (identity-token gated the same as obligation cancel/waive). On success, invalidates `queryKeys.tenants.{obligations,financialTimeline,advance,full,overview}` and calls the page's `refetch()`. `currentRent` is read from `tenant?.monthly_rent ?? overview?.rent` — the same already-loaded proxy the page already uses elsewhere (e.g. `hasActivePlan`) — since the page does not separately load the agreement's `contract_rent` field; **Unknown / needs clarification:** whether `tenant.monthly_rent` gets kept in sync when a rent change updates `agreement.contract_rent` (the backend service only writes `contract_rent`), which could make this displayed value stale after a change until some other sync path runs.
